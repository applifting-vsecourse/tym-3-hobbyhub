# ADR-0025: Unikátní přezdívka

**Status:** Přijato ✅ <br>
**Datum:** 15-11-2026 <br>
**Autor:** Marek

## Kontext

- Issue [#212](https://github.com/applifting-vsecourse/tym-3-hobbyhub/issues/212): uživatel při registraci chce mít jistotu, že nebude mít stejnou přezdívku jako někdo jiný.
- [ADR-0011](adr-0011.md) zavedlo jedno pole „jméno / přezdívka“ (`displayName`, v databázi `user.name` BetterAuthu) bez unikátnosti. Dva lidé se mohou jmenovat stejně a v seznamu účastníků je nikdo nerozliší.
- Projekt už má zapnutý plugin `username` BetterAuthu. Ten drží sloupce `username` (s unikátním indexem) a `displayUsername`, aplikace je ale nepoužívala; vyplňoval je jen seed.

## Rozhodnutí

```
User
- displayName: String            // přezdívka tak, jak ji uživatel napsal (displayUsername = name)
- username: String {unique}      // displayName malými písmeny, porovnává se při unikátnosti
- usernameChangedAt: DateTime [0..1]   // poslední změna v profilu
```

- Přezdívku budeme držet v pluginu `username`: `username` je malými písmeny a unikátní, `displayUsername` je tvar, jak ji uživatel napsal. `name` je vždy kopie `displayUsername`, takže zbytek aplikace přezdívku čte jako dosud.
- Dvě přezdívky jsou stejné bez ohledu na velikost písmen: „Kachna“ = „kachna“.
- Přezdívka má 3–30 znaků z `a–z`, `A–Z`, `0–9`, `_` a `.` (výchozí pravidlo pluginu). Nesmí obsahovat slova admin, administrator, moderator, hobbyhub, support, podpora, superadmin, spravce a system a nesmí být přesně „mod“. Rezervovaná slova platí jen pro nově zvolené přezdívky.
- Unikátnost hlídá registrace i úprava profilu. Formuláře se během psaní ptají endpointu pluginu `/is-username-available` (rate limit 60 za minutu na IP), server pravidla ověří znovu při uložení.
- Přezdívka se mění jen v profilu (`PATCH /api/profile`), nejvýš jednou za 30 dní od poslední změny tam. Registrace ani migrace se jako změna nepočítají. Obecný `/update-user` BetterAuthu přezdívku měnit nesmí.
- Přezdívka není přihlašovací údaj: `/sign-in/username` je zablokovaný, přihlašuje se jen e-mailem.
- Migrace dá přezdívku každému existujícímu účtu: platný `username` ze seedu zůstane, ostatním vznikne z `name` („Jan Novák“ → „JanNovak“; při shodě číslo, „JanNovak2“; kratší než 3 znaky → „hrac1“). `name` se přepíše na stejnou hodnotu. Uživatele o změně neupozorňujeme.
- Databáze drží stejná pravidla jako CHECK: formát `username`, `lower(displayUsername) = username` a `name = displayUsername`.

## Zvažované možnosti

- **A: Unikátní `user.name`**
  - Výhody: nejmenší změna, jména s mezerou a diakritikou zůstanou.
  - Nevýhody: unikátnost bez ohledu na velikost písmen by potřebovala vlastní index a vlastní kontrolu dostupnosti; plugin `username` by dál ležel ladem.
- **B: Plugin `username`, `name` jako kopie (zvoleno)**
  - Výhody: unikátní index, normalizace na malá písmena i endpoint na dostupnost už existují; zbytek aplikace čte `name` beze změny.
  - Nevýhody: přezdívka nesmí mít mezery ani diakritiku a existující jména se migrací změní; tři sloupce se musí držet v souladu (hlídají to CHECKy).
- **C: Volné jméno a k němu unikátní @handle**
  - Výhody: zachová skutečná jména.
  - Nevýhody: dvě pole v registraci i profilu, proti jednomu poli z ADR-0011.

## Důsledky

- Kdokoli, i nepřihlášený, zjistí přes kontrolu dostupnosti, jestli přezdívka existuje. Víc o účtu nezjistí a přezdívky organizátorů jsou veřejné už v detailu akce. Zapsáno v [matici viditelnosti](../visibility-matrix/README.md).
- Účty, které nevznikly registrací (testy), mohou mít `username` prázdný; CHECKy prázdnou hodnotu pustí.
- Přihlášení přes Google (F-03.6) bude muset přezdívku při prvním přihlášení vyžádat nebo vygenerovat stejně jako migrace.
- Seed nastavuje přezdívky přímo v databázi, takže smí použít i rezervovaná slova („superadmin“, „PondAdmin“).
