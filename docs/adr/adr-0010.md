# ADR-0010: Moderace a administrace

**Status:** Navrženo ❓ <br>
**Datum:** 11-10-2026 <br>
**Rozhodující:** Marek

## Kontext
Z feature breakdownu v0.4 (vše MVP):

- Uživatel nahlásí akci nebo uživatele: důvod, volitelný text, vazba na obsah; skupiny se nenahlašují (F-10.1).
- Správce má oddělené oprávnění a MFA; zásahy se zaznamenávají: kdo, kdy a co změnil (F-11.1).
- Správce zkontroluje ověření e-mailu, zablokuje účet a vyřídí smazání a export údajů (F-11.2, F-04.5).
- Správce skryje nebo zruší akci a zásah se zaznamená (F-11.3).
- Fronta nahlášení se stavy nové / řeší se / vyřešeno, odpovědný správce a poznámka k řešení (F-11.4).
- Důvody nahlášení jsou pevný číselník (F-13.5).

Sitemapa v0.3 vede administraci jako „MVP navržené dodavatelem“. Model dosud žádnou část moderace neměl.

## Rozhodnutí
Nový balíček `moderation`:

```
Administrator
- name: String
- email: String
- createdAt: DateTime

Report
- text: String [0..1]
- createdAt: DateTime
- status: ReportStatus
- resolutionNote: String [0..1]
- resolvedAt: DateTime [0..1]
Report "*" ---- "1"    User           (role reporter)
Report "*" ---- "0..1" Event          (role targetEvent)
Report "*" ---- "0..1" User           (role targetUser)
Report "*" ---- "1"    ReportReason   (role reason)
Report "*" ---- "0..1" Administrator  (role assignee)

ReportReason                            // číselník (ADR-0002)
- name: String
«enumeration» ReportStatus: NEW, IN_PROGRESS, RESOLVED

AuditLogEntry
- createdAt: DateTime
- action: String
- targetType: String
- targetId: String
- description: String [0..1]
AuditLogEntry "*" ---- "1" Administrator  (role admin)

DataRequest
- type: DataRequestType
- requestedAt: DateTime
- resolvedAt: DateTime [0..1]
DataRequest "*" ---- "1"    User           (role user)
DataRequest "*" ---- "0..1" Administrator  (role resolvedBy)
«enumeration» DataRequestType: EXPORT, DELETION
```

Omezení:
- `{právě jeden z targetEvent, targetUser je vyplněn}`, `{reporter ≠ targetUser}`, `{status = RESOLVED ⇔ resolvedAt je vyplněn}` u `Report`
- `{resolvedAt je vyplněn ⇔ resolvedBy je vyplněn}` u `DataRequest`

Všechny vazby jsou asociace, ne kompozice. Nahlášení, záznamy zásahů a žádosti o data musí přežít smazání (anonymizaci) uživatele i akce, protože slouží jako doklad (F-11.1, F-12.4).

## Zvažované možnosti
**Správce**
- **A: Role nebo příznak v `User`**
  - Výhody: jedna tabulka uživatelů.
  - Nevýhody: míchá veřejné účty s provozními; F-11.1 chce oddělené oprávnění a přihlášení.
- **B: Samostatná třída `Administrator` (zvoleno)**
  - Výhody: oddělení podle F-11.1; správce nemá profil, akce ani žádosti.
  - Nevýhody: správce, který chce aplikaci používat, potřebuje i běžný účet.

**Cíl nahlášení**
- **A: Dvě nepovinné asociace s omezením na právě jednu (zvoleno)**
  - Výhody: vazby jsou v diagramu vidět; dva typy cíle stačí (F-10.1).
  - Nevýhody: další typ cíle znamená další asociaci.
- **B: Obecný `targetType` a `targetId`**
  - Výhody: libovolný cíl bez změny modelu.
  - Nevýhody: vazba není v modelu vidět ani hlídaná.
- **C: Abstraktní nadtřída `Reportable` pro `Event` a `User`**
  - Nevýhody: zavádí dědičnost do hlavních tříd kvůli jedné vazbě.

Záznam zásahů naopak používá obecný cíl (možnost B), protože zásah může mířit na cokoli (uživatel, akce, nahlášení, žádost o data) a slouží jen jako log.

## Důsledky
- Více rolí správce, vlastní dashboard a SLA reporting jsou odložené (F-11.1, F-11.4).
- MFA a přihlášení správce zajistí autentizační služba (ADR-0011).
