# ADR-0003: Oddělení žádosti o účast od účasti na akci

**Status:** Navrženo ❓ <br>
**Datum:** 11-10-2026 <br>
**Rozhodující:** Marek

## Kontext
První verze modelu měla jednu třídu `Participation`. Ta držela vztah člověka k akci od podání žádosti přes schválení, potvrzení a odhlášení až po docházku a hodnocení.

Na model působí tyto požadavky z feature breakdownu:

- Registrovaný uživatel podává žádost o účast, volitelně se zprávou organizátorovi (F-06.1, F-08.1).
- Organizátor žádost schválí, nebo zamítne s volitelným důvodem. Schvalování je ruční, nebo automatické podle nastavení akce (F-05.5, F-05.7).
- Schválený účastník potvrzuje účast na výzvu před akcí a může se odhlásit, po storno lhůtě s postihem (F-05.8, F-06.4, F-05.14, F-10.5).
- Organizátor může ručně přidat účastníka mimo aplikaci jen jménem (F-05.6).
- Po naplnění kapacity vzniká pořadník náhradníků (F-05.9).
- Organizátor označuje docházku a po akci se hodnotí (F-05.11, F-06.6).
- Uživatel vidí přehled svých přihlášek se stavy čeká / schváleno / zamítnuto / náhradník / zrušeno / zúčastnil se / nedorazil (F-06.3).

V jedné třídě se tak míchaly dva životní cykly s různými aktéry. O žádosti rozhoduje organizátor, účast pak spravuje hlavně účastník. Projevilo se to např. tím, že třída měla vedle sebe `decidedAt` (rozhodnutí organizátora) a `confirmedAt` (potvrzení účastníka), a stavy žádosti (`PENDING`, `REJECTED`) byly ve stejném výčtu jako stavy účasti (`ATTENDED`, `NO_SHOW`).

Navíc ne každá účast vzniká z žádosti. Host přidaný ručně (F-05.6) žádost nemá a pozvaný člen skupiny (ADR-0004) také ne.

## Rozhodnutí
Žádost o účast a účast budeme modelovat jako **dvě samostatné třídy**.

```
«enumeration» RequestStatus: PENDING, APPROVED, REJECTED

ParticipationRequest                   // žádost (F-06.1, F-05.7)
- status: RequestStatus
- message: String [0..1]               // F-08.1
- requestedAt: DateTime
- decidedAt: DateTime [0..1]
- rejectionReason: String [0..1]

Participation                          // účast
- status: ParticipationStatus          // INVITED, APPROVED, WAITLISTED, DECLINED,
                                       // CANCELLED, ATTENDED, NO_SHOW
- guestName: String [0..1]
- waitlistPosition: Integer [0..1]
- offerExpiresAt: DateTime [0..1]
- confirmedAt: DateTime [0..1]
- cancelledAt: DateTime [0..1]
- isLateCancellation: Boolean
- checkInCode: String [0..1]

Event ◆ "0..*" ParticipationRequest    (role requests)
Event ◆ "0..*" Participation           (role participations)
ParticipationRequest "*" ---- "1" User
ParticipationRequest "0..1" ---- "0..1" Participation  (role request / participation)
```

- Účast vzniká schválením žádosti, pozváním člena skupiny (ADR-0004), nebo ručním přidáním hosta (F-05.6). Odkud vznikla, plyne z vazeb (`request`, `user`, `guestName`), další atribut není potřeba.
- Hodnocení, hlasy v anketě a reakce na nástěnce zůstávají vázané na `Participation`. Hlasovat a reagovat smějí jen účastníci (F-05.13), hodnotit jen ti, kdo se zúčastnili (F-06.6).
- Přehled přihlášek (F-06.3) se skládá z obou tříd: „čeká“ a „zamítnuto“ jsou stavy žádosti, ostatní stavy jsou stavy účasti.
- Stav „potvrzeno“ (F-05.6, F-05.8) není samostatný literál, je to `APPROVED` + vyplněné `confirmedAt`.

## Zvažované možnosti
- **A: Jedna třída `Participation` pro žádost i účast (původní stav)**
  - Výhody: méně tříd a vazeb.
  - Nevýhody: míchá dva životní cykly a aktéry; jeden výčet stavů pro žádost i účast; atributy žádosti zůstávají prázdné u hostů a pozvaných; špatně se vyjadřuje, že účast může vzniknout i bez žádosti.
- **B: Samostatné třídy `ParticipationRequest` a `Participation` (zvoleno)**
  - Výhody: každá třída má jeden životní cyklus a vlastní výčet stavů; účast bez žádosti (host, pozvaný člen) je přirozená; jednoznačné, kdo co rozhoduje.
  - Nevýhody: o třídu a výčet víc; přehled přihlášek (F-06.3) se skládá ze dvou zdrojů; je potřeba hlídat konzistenci mezi žádostí a účastí (omezení níže).
- **C: Společná nadtřída a dědičnost (žádost a účast jako podtřídy)**
  - Výhody: společné atributy na jednom místě.
  - Nevýhody: žádost a účast nemají skoro nic společného kromě uživatele a akce; dědičnost by nedávala smysl, protože se z jedné instance nestává druhá.

## Důsledky
- Snazší: jasné stavové diagramy pro žádost a pro účast; přímé přidání do akce bez žádosti (ADR-0004).
- Omezení v modelu:
  - `{request je vyplněn ⇒ user = request.user}`
  - `{ParticipationRequest.status = APPROVED ⇔ participation existuje}`
  - `{decidedAt je vyplněn ⇔ status ≠ PENDING}`, `{rejectionReason jen při REJECTED}`
  - `{uživatel má u jedné akce nejvýš jednu žádost ve stavu PENDING}` (výchozí volba)
- Otevřené: F-06.3 ani jiná položka breakdownu neřeší, zda uživatel může čekající žádost stáhnout (u skupin to F-07.7 umožňuje). Pokud ano, přibude stav `WITHDRAWN`.
