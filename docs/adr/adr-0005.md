# ADR-0005: Spoluorganizátoři akce a samopřidání organizátorů do akce

**Status:** Navrženo ❓ <br>
**Datum:** 11-10-2026 <br>
**Autor:** Marek

## Kontext

Akci dosud spravuje jen jeden organizátor (`Event.organizer`). U větších nebo pravidelných akcí na to organizátor nemusí stačit sám (schvalování žádostí, docházka, nástěnka).

Z feature breakdownu:

- Breakdown v0.4 spoluorganizátora nezná. Jediná zmínka z v0.2 (F-04.5 „předat spoluorganizátorovi“) ve v0.4 zmizela, F-04.5 teď říká jen „před smazáním vyřeší budoucí pořádané akce“. Spoluorganizátoři jsou proto čistě naše rozšíření.
- Organizátor schvaluje žádosti (F-05.7), upravuje a ruší akci (F-05.10). Docházka (F-05.11), nástěnka (F-05.13), topování (F-05.12, F-04.6) a hodnocení účastníků (F-06.6) jsou ve v0.4 Nice to have.
- Breakdown neříká, zda se organizátor počítá do kapacity a obsazenosti akce (F-05.1, F-02.3).

Druhá otázka vznikla s ADR-0003: organizátor, který se chce akce sám účastnit, by si musel podat žádost a sám si ji schválit, což nedává smysl.

## Rozhodnutí

**1. Spoluorganizátoři**

- Akce má právě jednoho hlavního organizátora (`organizer [1]`) a libovolný počet spoluorganizátorů (`coOrganizers [0..*]`).
- Spoluorganizátory přidává a odebírá jen hlavní organizátor. Může to být kterýkoli uživatel, u akce skupiny jen člen skupiny.
- Spoluorganizátor smí: upravit akci, schvalovat a zamítat žádosti, spravovat pořadník a zvát členy skupiny (ADR-0004), posílat výzvu k potvrzení, označit docházku a psát na nástěnku.
- Jen hlavní organizátor smí: zrušit nebo smazat akci, spravovat spoluorganizátory, topovat akci a hodnotit účastníky.
- Při smazání účtu (F-04.5) může organizátor budoucí akci předat spoluorganizátorovi: ten se stane `organizer` a přestane být v `coOrganizers`. Druhou možností je akci zrušit.

**2. Organizátoři jako účastníci**

- Organizátor ani spoluorganizátor nejsou účastníky automaticky. Pokud se chtějí akce účastnit, přidají se sami (`joinAsOrganizer`). Vznikne účast ve stavu `APPROVED` bez žádosti.
- Přidat se lze jen před `startAt` a jen když je volné místo.
- Po přidání se počítají do kapacity, obsazenosti, statistik účastníků (F-06.7) i metrik (F-11.6) jako kdokoli jiný.
- Organizátor ani spoluorganizátor nehodnotí akci, kterou vedou (`EventReview`), aby si nezvyšovali vlastní hodnocení (F-06.6).

**Dopad na model**

```
Event "*" ---- "1"    User   (role organizer)       // beze změny
Event "*" ---- "0..*" User   (role coOrganizers)    // nové

Event
+ joinAsOrganizer(user: User): Participation
+ addCoOrganizer(user: User)
+ removeCoOrganizer(user: User)
+ transferOrganizer(newOrganizer: User)
```

Omezení:

- `{organizer ∉ coOrganizers}`
- `{group je vyplněna ⇒ každý coOrganizer je členem group}`
- `{joinAsOrganizer: user = organizer ∨ user ∈ coOrganizers; jen před startAt a při /freeSpots > 0}`
- `{EventReview: participation.user ≠ event.organizer ∧ participation.user ∉ event.coOrganizers}`
- Omezení účasti bez žádosti z ADR-0004 se rozšiřuje: `{request je prázdný ∧ user je vyplněn ⇒ user = event.organizer ∨ user ∈ event.coOrganizers ∨ (event.group je vyplněna ∧ user je členem event.group)}`

Práva se v diagramu tříd nemodelují. Patří do matice oprávnění a viditelnosti (F-13.8).

## Zvažované možnosti

**Spoluorganizátoři**

- **A: Jen jeden organizátor (původní stav)**
  - Výhody: nejjednodušší, jednoznačná odpovědnost.
- **B: Asociace `coOrganizers` vedle `organizer` (zvoleno)**
  - Výhody: jednoduchá změna modelu; hlavní organizátor zůstává jednoznačný pro rušení akce a platby (F-04.6); předání akce je jen přesun mezi rolemi.
  - Nevýhody: práva spoluorganizátora jsou pevně daná, nejde je nastavit jednotlivě.
- **C: Třída `EventRole` (uživatel, akce, role, sada oprávnění)**
  - Výhody: práva nastavitelná pro každého spoluorganizátora zvlášť.
  - Nevýhody: složitější model i UI; breakdown nic takového nepožaduje.

**Organizátor jako účastník**

- **A: Organizátor je vždy automaticky účastníkem**
  - Výhody: nic se nemusí dělat ručně.
  - Nevýhody: neplatí pro organizátory, kteří akci jen pořádají (trenér, správce); zbytečně zabírá místo.
- **B: Organizátor se nikdy nepočítá**
  - Výhody: jednoduché.
  - Nevýhody: obsazenost „7/10“ neodpovídá realitě, když organizátor hraje.
- **C: Organizátor a spoluorganizátoři se mohou sami přidat (zvoleno)**
  - Výhody: odpovídá realitě obou typů organizátorů; žádné schvalování sám sobě; statistiky a metriky počítají správně bez zvláštních pravidel.
  - Nevýhody: jeden krok navíc pro organizátora, který hraje.

## Důsledky

- Snazší: sdílená správa akce; předání akce při smazání účtu (F-04.5).
- Toto rozhodnutí **rozšiřuje feature breakdown** (práva spoluorganizátora, samopřidání). Breakdown se nemění; rozšíření je potřeba potvrdit s PO.
- Navazující práce: doplnit roli spoluorganizátora do matice viditelnosti (F-13.8), např. zda vidí kontakty potvrzených účastníků jako organizátor (F-04.2).
- Otevřené: notifikace pro spoluorganizátory (nové žádosti F-09.2 dostává organizátor; dostávají je i spoluorganizátoři?).
